## 1. Зачем вообще нужен Docker?

### 1.1 Проблема окружения

Представь: локально проект работает идеально, деплоишь на VPS — и начинается хаос.

**Без Docker:**
```
Локально: Python 3.11 + PostgreSQL 16 + все библиотеки
Сервер:  Python 3.9  + PostgreSQL 13 + половины библиотек нет
Результат: ошибки при запуске
```

Знакомо?

**С Docker:**
- Ты описываешь среду в `Dockerfile`/`compose.yml`
- Собираешь образ
- Запускаешь один и тот же контейнер где угодно
- Получаешь одинаковый результат

### 1.2 Docker — это «контейнер для приложения»

**Аналогия:**

Docker = **грузовой контейнер в логистике**

- Что внутри, не важно перевозчику
- Формат контейнера стандартный
- Его можно перевезти поездом, кораблём, фурой

С приложениями так же:
- Ты упаковал код + зависимости + настройки
- И запускаешь пакет на локалке, VPS, облаке

### 1.3 Зачем Docker нужен при vibe-coding?

**1. AI генерирует код быстро, но среда часто «плавает»**
- Нужен стабильный способ запуска

**2. Быстрые эксперименты**
- Не ломаешь систему
- Снес контейнер — начал заново

**3. Деплой без сюрпризов**
- «Работает локально» ≈ «работает на сервере»

### 1.4 Docker vs Виртуальная машина

| Что | VM | Docker |
|-----|----|--------|
| Изоляция | Полная ОС внутри | Изоляция процессов |
| Размер | Тяжелее | Легче |
| Старт | Медленнее | Быстрее |
| Ресурсы | Больше RAM/CPU | Меньше RAM/CPU |

## 2. Как работает Docker: базовая модель

### 2.1 Основная цепочка

```
Dockerfile -> Image -> Container
```

- `Dockerfile` = рецепт
- `Image` = шаблон по рецепту
- `Container` = запущенный экземпляр шаблона

### 2.2 Image vs Container

| Image | Container |
|-------|-----------|
| Неизменяемый шаблон | Запущенный процесс |
| Хранится на диске | Работает в памяти |
| Один образ на много запусков | Каждый запуск — новый контейнер |

### 2.3 Слои (Layers)

Docker-образ собирается слоями:

```
FROM python:3.11-slim     <- базовый слой
COPY requirements.txt .   <- слой 2
RUN pip install ...       <- слой 3
COPY . .                  <- слой 4
CMD ["python", "app.py"] <- слой 5
```

Почему это важно:
- кеш ускоряет пересборки;
- меньше повторной работы;
- экономия места.

### 2.4 Три сущности, которые нужно помнить

- **Container runtime**: запускает контейнеры
- **Network**: связывает контейнеры между собой
- **Volume**: сохраняет данные вне контейнера

## 3. Установка и настройка Docker

### 3.1 Проверка установки

```bash
docker --version
docker compose version
```

**Если видишь версии** — Docker установлен ✅

### 3.2 Базовая проверка работы

```bash
docker run hello-world
```

Если выводится приветственное сообщение — демо-контейнер успешно запустился.

### 3.3 Полезная диагностика

```bash
docker info
```

Показывает:
- информацию о daemon;
- доступные драйверы;
- состояние storage/network;
- системные лимиты.

## 4. Основные команды Docker

### 4.1 Работа с образами

```bash
docker pull python:3.11-slim
docker images
docker build -t my-app:latest .
docker rmi my-app:latest
```

**Что важно понимать:**
- `pull` скачивает готовый образ;
- `build` собирает образ из твоего `Dockerfile`;
- `rmi` удаляет локальный образ.

### 4.2 Работа с контейнерами

```bash
docker run --name my-app my-app:latest
docker run -d --name my-app my-app:latest
docker run -d -p 8080:80 nginx:stable

docker ps
docker ps -a
docker stop my-app
docker rm my-app
```

### 4.3 Логи и вход внутрь

```bash
docker logs my-app
docker logs -f my-app
docker exec -it my-app sh
```

Если в образе есть `bash`:

```bash
docker exec -it my-app bash
```

### 4.4 Быстрая очистка

```bash
docker system prune
```

Более агрессивно (осторожно):

```bash
docker system prune -a --volumes
```

## 5. Dockerfile — как описать окружение

### 5.1 Простой рабочий Dockerfile (Python)

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

### 5.2 Разбор строк

1. `FROM` — базовый образ
2. `WORKDIR` — рабочая директория в контейнере
3. `COPY requirements.txt .` — копируем файл зависимостей
4. `RUN pip install ...` — устанавливаем зависимости
5. `COPY . .` — копируем код
6. `CMD` — команда запуска

### 5.3 Почему порядок инструкций важен

Если сначала скопировать весь проект, а потом ставить зависимости — кеш ломается почти при любом изменении.

Лучше порядок:
1. копируем `requirements.txt`
2. ставим зависимости
3. копируем код

Так сборка быстрее.

### 5.4 .dockerignore

**Проблема:** `COPY . .` может затянуть мусор и секреты.

**Решение:** `.dockerignore`

```text
.git
.gitignore
__pycache__
*.pyc
.venv
.env
.vscode
.idea
*.log
node_modules
```

## 6. Docker Compose — несколько сервисов

### 6.1 Зачем нужен Compose

Когда у тебя не один контейнер, а связка сервисов:
- приложение
- база
- кеш
- воркер

Запускать вручную `docker run ...` неудобно.

`docker compose` описывает всё в одном файле и запускает одной командой.

### 6.2 Минимальный пример app + postgres

```yaml
services:
  app:
    build: .
    depends_on:
      - db
    environment:
      DB_HOST: db
      DB_PORT: 5432
      DB_USER: app
      DB_PASSWORD: app
      DB_NAME: app
    ports:
      - "8000:8000"

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:
```

### 6.3 Команды Compose

```bash
docker compose up -d
docker compose ps
docker compose logs -f
docker compose down
docker compose up -d --build
```

### 6.4 Важный нюанс про depends_on

`depends_on` гарантирует порядок старта контейнеров, но НЕ гарантирует, что БД уже готова к подключениям.

Нужно:
- retry в приложении;
- healthcheck;
- ожидание готовности сервиса.

## 7. Volumes и данные

### 7.1 Почему данные пропадают

Контейнеры эфемерны: удалил контейнер — удалился его writable-слой.

### 7.2 Именованный volume

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:
```

**Плюс:** данные базы переживут пересоздание контейнера.

### 7.3 Bind mount для разработки

```yaml
services:
  app:
    build: .
    volumes:
      - ./:/app
```

**Когда использовать:**
- в dev, чтобы код на хосте сразу отражался в контейнере.

## 8. Частые кейсы

### 8.1 Запуск локально API + БД

**Шаги:**
1. Создать `Dockerfile`
2. Создать `compose.yml`
3. Запустить `docker compose up -d --build`
4. Проверить логи `docker compose logs -f`

### 8.2 Обновление приложения на VPS

```bash
git pull
docker compose up -d --build
docker image prune -f
```

### 8.3 Очистка системы от мусора

```bash
docker system df
docker system prune
```

### 8.4 Проверка почему сервис не отвечает

Чек-лист:
1. `docker compose ps`
2. `docker compose logs -f`
3. Проверка портов (`ports` в compose)
4. Проверка env-переменных
5. Проверка сети (имена сервисов)

## 9. Docker в работе с AI (практика vibe-coding)

### 9.1 Типовой workflow

1. AI генерирует код и Docker-конфиг
2. Ты запускаешь:

```bash
docker compose up -d --build
```

3. Если ошибка, снимаешь логи:

```bash
docker compose logs -f
```

4. Передаешь ошибку AI, получаешь фиксы
5. Повторяешь цикл

### 9.2 Почему это работает

- AI лучше исправляет, когда среда стабильна
- Ошибки воспроизводимы
- Проще командная работа и деплой

### 9.3 Что важно контролировать вручную

- секреты и токены;
- открытые порты;
- права доступа;
- версии образов и зависимостей.

## 10. Работа в команде (базовые правила)

1. Договоритесь о едином `compose.yml` и naming (`app`, `db`, `redis`).
2. Не храните `.env` в Git.
3. Фиксируйте версии образов (не только `latest`).
4. Любые изменения Docker-конфигов сопровождайте короткой инструкцией в README.
5. Проверяйте запуск «с нуля» перед merge.

Мини-чек перед PR:
- `docker compose up -d --build` проходит
- сервисы healthy
- миграции инициализируются
- нет лишних портов наружу

## 13. Частые вопросы (FAQ)

### Вопрос: Docker и Docker Compose — это одно и то же?

Нет.
- Docker — движок контейнеров.
- Docker Compose — инструмент для запуска нескольких сервисов.

### Вопрос: Можно ли без Docker, если проект маленький?

Можно, но на этапе деплоя и командной работы Docker обычно экономит время и нервы.

### Вопрос: Нужно ли публиковать порт БД наружу?

Обычно нет. Если БД нужна только приложению, оставляй ее внутри docker-сети.

### Вопрос: Почему контейнер выходит сразу после старта?

Завершилась главная команда процесса (`CMD`/`ENTRYPOINT`). Проверь логи и команду запуска.

### Вопрос: Как не терять данные Postgres?

Используй named volume и делай регулярные бэкапы.

### Вопрос: Какой минимум для старта?

- `Dockerfile`
- `compose.yml`
- умение читать логи
- 4 команды: `up`, `logs`, `ps`, `down`
